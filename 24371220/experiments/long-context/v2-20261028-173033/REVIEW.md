## 源码题失败链

1. 三个目标文件完成了工具层全文读取，修改前 pytest 实际执行，基线为 50 failed、10 passed（未实现新增要求的初始状态）。
2. 模型反复使用位置参数 `get_evidence("...")`、字典 `.get()` 等执行器不支持的表达式；另有响应未采用要求的单个 Python 代码块。AST 在整块执行前验证，因此这些错误阻止该块中的工具调用。
3. 执行器打印额度 `output_len` 及 `output_truncated` 没有在每轮重置。从第10轮起可见打印截断标记，重复读取和打印进一步消耗轮次。完整证据仍可能通过上下文进入请求，不能说所有源码都未送入模型。
4. 最终20轮预算耗尽，未写代码、未完成修复后验证。

课程源码阅读检查将各关键位置列为缺失。只读核对 `tools/source_context.py` 后发现：没有首次写入时决策索引为 -1，因而这一判定不能独立证明此前完全没有入模；它是未写入状态的下游结果。不能据此改分，也不修改评测器。`_emit_logs` 等必要位置的真实覆盖仍需在修复后核验。

## 论文题失败链

课程 `阅读检查.json` 确认提取并进入真实请求的是第1–39页，共39/52页；未保存五主题 `section_note`，未生成报告。

第23轮通过 `get_evidence` 将 PDF 证据保存到变量 `r32`；该记录带 `path=paper.pdf` 和 `file_hash`，执行器将其登记为跨轮来源。从第24轮（run.log seq 238）起，后续有效代码块在执行前校验该变量来源时调用 `WorkspaceTools.current_hash`。该函数错误地复用了文本读取函数 `_read_bytes`，PDF 中的 NUL 字节触发 `binary files are not supported`。错误发生在 worker 执行前，令后续工具操作无法推进。响应格式和受限语法错误又消耗了部分轮次，最终40次预算耗尽。

这属于实现缺陷，而非 PDF 提取工具失效，也不能仅归因于模型能力。
