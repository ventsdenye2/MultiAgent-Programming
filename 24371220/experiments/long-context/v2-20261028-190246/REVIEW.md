## 源码题：客户端提前超时

Agent 的请求超时配置为约90秒。本轮第6次请求从请求日志到错误日志间隔89.39秒，随后记录 `MODEL_REQUEST_FAILED: timed out`。前5次返回正常，没有动作解析错误或 code_execution 错误。

课程转发器仍继续接收第6次请求，最终保存了真实响应；6次记录均为HTTP 200且有合法服务端 usage。因此课程汇总用量完整，而 Agent 自己的汇总为不完整：两者观察的结束点不同，不能删除或补写 Agent 未收到的响应。

本轮真实用量：输入 **49,684 token**，输出 **1,624 token**，合计 **51,308 token**。以课程保存的原始响应核算，包含第6次请求。该数字不是成功完成任务的效率成绩，不估算费用，也不与完整运行的输入量直接比较效率。

## 论文题：本地 PDF 预检超时

课程入口在创建论文题结果目录和调用模型之前，执行 `pdftotext -layout -enc UTF-8 -f 1 -l 76 ... -`，其内置30秒超时触发。故不存在本轮论文题 result.json，也没有论文模型请求。

| Windows挂载盘原始PDF | 35.13秒 | 0 | 294,602 | 76 |
| 项目内临时tmpfs中的同一PDF副本 | 0.39秒 | 0 | 294,602 | 76 |

tmpfs副本复制耗时0.15秒，诊断结束后已清理并卸载。原始测量见 [pdf-preflight-probe.json](pdf-preflight-probe.json) 与 [pdf-native-probe.json](pdf-native-probe.json)。这是单次顺序对照，缓存及系统状态可能不同；结果支持下一轮优先使用Linux原生文件系统，但不能当作严格性能基准，也不能据此解释模型请求的网络超时。
