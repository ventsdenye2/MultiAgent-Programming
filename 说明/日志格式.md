# run.log 日志格式

这份说明供实现日志时查阅。测试通过后，评测还会检查智能体是否执行了题目要求的步骤；run.log 就是这些检查的依据。[使用与自测步骤](../README.md)在 README 中。

## 怎么保存

由自行实现的智能体程序在启动目录生成 `run.log`，评测工具读取它来检查执行过程。日志使用 UTF-8 JSONL：每行一个 JSON 对象，每次真实操作完成就追加记录。请求、响应、工具参数和结果完整保存，鉴权信息和密钥不记录。不要只保留动作摘要，不要事后补写。

`patch.diff` 同样由智能体程序保存在启动目录。程序统一负责日志和补丁的保存，题目执行过程中不必再通过写文件工具另建、覆盖或补写这些文件。

内部工具叫什么、API 用什么格式，由你决定；写入日志时映射成下面的事件。可以增加字段。

| event | 必需字段或内容 |
| --- | --- |
| model_request | body 保存完整真实请求体；messages 保存本次实际上下文，格式见下文 |
| model_response | response 保存完整 API 返回 JSON；也可用 raw 保存该 JSON 的完整字符串 |
| model_error | 保存模型请求失败的真实错误；每个请求都有对应响应或错误记录 |
| usage | actual_model 和 API 上报的 usage；未上报时如实记为未知 |
| file_read | path 和完整的 content |
| file_write | path 和完整的 content |
| command_result | 实际 argv 数组、整数 rc、完整 stdout 和 stderr；无输出写空字符串 |
| plan | items 数组，各项含 title 与 status，status 使用 todo、doing、done |
| context_clip / context_drop / context_summary | 采用的方法、触发原因、处理前后信息，以及保留、舍弃或摘要的内容 |

## 请求、响应与用量

messages 每项保存 role、content 及原始工具调用字段。如果真实请求的 body.messages 已符合这个结构，直接使用；否则在事件外层另写 messages，映射本次实际上下文，不能省略内容。

示例仅说明结构，正式运行须记录自己的真实请求和完整返回：

```jsonl
{"event":"model_request","body":{"model":"实际模型ID","messages":[{"role":"user","content":"实际题面与上下文"}],"stream":false}}
{"event":"model_response","response":{"model":"返回的实际ID","choices":[{"message":{"role":"assistant","content":"实际返回内容"}}],"usage":{"prompt_tokens":10,"completion_tokens":5,"total_tokens":15}}}
{"event":"usage","actual_model":"返回的实际ID","usage":{"prompt_tokens":10,"completion_tokens":5,"total_tokens":15}}
```

usage 中的 prompt_tokens、completion_tokens、total_tokens 使用 API 上报的非负整数，total 为前两项之和。README 写清字段映射；缺失时记录未知或不完整，不估算、不补0。actual_model 使用 API 返回的实际模型标识。

## 工具操作

```jsonl
{"event":"file_read","path":"module.py","content":"实际读取的完整文件内容"}
{"event":"file_write","path":"module.py","content":"实际写入的完整文件内容"}
{"event":"command_result","argv":["python","-m","pytest","-q"],"rc":1,"stdout":"实际完整输出","stderr":""}
{"event":"plan","items":[{"title":"修复计算","status":"doing"},{"title":"验证回归","status":"todo"}]}
```

也可以使用 tool_result：action 保存 tool（read、write、command、plan）及参数，result 保存结果。读文件内容放在 result.content，写文件内容放在 action.content，命令参数放在 action.argv，rc、stdout、stderr 放在 result；计划放在 action.items。工具错误放在 result.error，不算成功操作。

## 第四题的执行顺序怎么记录

计划的前两项依次对应净额修复和 CSV 导出。同一项的 title 和顺序保持不变，更新 status 即可。

按真实执行顺序记录：净额修复写入 → 完整测试 → 第一项计划标为 done → 开始写入 CSV 实现 → 最终完整测试 → 计划全部标为 done。

中间测试仍运行完整 `python -m pytest -q`，日志中保留所有失败明细和最后的数量汇总。此时 CSV 尚未实现造成的失败是预期结果，但净额对应的测试必须通过；不能只保存“2 passed”或一段摘要。评测会结合 `ledger.py` 的完整写入内容、测试输出和计划顺序检查这一步，最终10个测试全通过不能代替中间记录。

若 failed_checks 中出现 separate_subtask_writes，检查是否先单独写入净额修复；出现 net_verified_before_csv，检查中间完整测试及其输出；出现 plan_updated_before_csv，检查是否在中间验证后、实现 CSV 前更新计划。

## 第五题的长输出怎么记录

日志和模型上下文各有用途：日志保留完整执行结果，模型请求只包含本次实际发送的内容。例如，命令输出15000字符，可以全部写进 command_result.stdout，再裁剪后发给模型。

采用裁剪、删除或摘要时记录相应事件，说明触发原因、原始长度和处理内容。下一次 model_request 的 messages 必须与实际发送的上下文一致。不能先发出超限请求，再补一条裁剪记录。

第五题每次请求的 messages.content 字符数之和不超过16000。字符串按字符数计算；列表 content 按 `json.dumps(content, ensure_ascii=False)` 默认分隔符序列化后的长度计算。不是 token 数，也不包含日志中另存的完整原输出。

## 文件边界

`run.log` 和 `patch.diff` 必须是普通文件，不能是符号链接。补丁须能在初始仓库上用 GNU patch 还原最终改动。

评测器负责写 agent_stdout.txt、agent_stderr.txt、changes.json、repo_after、pytest_output.txt、validation_baseline_output.txt、junit.xml、evidence.json、patch_check.txt 和 result.json，智能体不要创建或覆盖这些文件。业务仓库中只修改 task.md 允许的文件；不要为了保存日志而额外改业务仓库。
